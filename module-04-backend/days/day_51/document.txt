CampusConnect
Complete Project Documentation
Project Type: Student Community Web Application
Framework: Next.js
Author: Hildana Asfaw
Role: Full Stack Developer

1. Introduction
CampusConnect is a student community web application developed using Next.js. It provides a centralized platform where students can discover campus events, explore learning resources, read announcements, and create events of their own.
The application also includes an administrative interface that allows administrators to manage announcements and review student resource access requests.
The project focuses on improving communication, information sharing, and student engagement through a simple, responsive, and user-friendly digital platform.
2. Project Objectives
The main objectives of CampusConnect are to:
•	Provide students with easy access to campus information.
•	Make campus events easier to discover and organize.
•	Provide access to educational resources.
•	Allow students to request learning materials.
•	Give administrators tools to manage announcements and resource requests.
•	Demonstrate practical implementation of modern web development technologies.
3. System Overview
CampusConnect has two main user experiences:
Student Interface
Provides access to student activities, profiles, events, announcements, and learning resources.
Administrator Interface
Provides administrative functionality for reviewing resource requests and managing campus announcements.
These interfaces use separate sign-in experiences and separate browser-stored sessions.

4. Student Management
4.1 Student Authentication
The student authentication functionality provides registration and sign-in.
During registration:
1.	The student enters their name, email, and password.
2.	The application validates the submitted information.
3.	The student account information is saved in browser Local Storage.
4.	A student session is created.
5.	The student is redirected to the dashboard.
During sign-in:
1.	The student enters their credentials.
2.	The application checks them against the saved account information.
3.	If the credentials match, a session is created.
4.	The student is redirected to the requested page or dashboard.
5.	If authentication fails, an error message is displayed.
The current implementation is intended for demonstration purposes and does not provide production-grade authentication security.
4.2 Student Dashboard
The dashboard is the central area of the student experience.
It provides access to:
•	Campus events.
•	Learning resources.
•	Announcements.
•	Student profile information.
•	Event creation.
The dashboard also displays a personalized welcome message and summaries of available application information.


4.3 Student Profile
The profile page provides a view of the student's account information.
It allows the application to present student-specific information based on the current saved session.
4.4 Campus Event Management
The event management functionality allows students to discover and create campus activities.
Students can:
•	Browse available events.
•	View event descriptions.
•	Check event dates and times.
•	View event locations.
•	Search for events.
•	Filter events by category.
•	Open individual event detail pages.
•	Submit new campus events.
The event creation form validates the submitted information before saving it.
Newly created events are stored in browser Local Storage in the current implementation.
5. Administrator Management
5.1 Administrator Authentication
CampusConnect provides a separate administrator sign-in experience.
Administrators access their own administrative area independently from the student interface.
The application uses a separate administrator session key rather than treating a student session as an administrator session.
This separation organizes administrative functionality and provides different user experiences.
The current implementation uses browser Local Storage for the administrator session. It is a prototype access check, not secure server-side authorization.




5.2 Admin Dashboard
The administrative dashboard provides access to management functionality.
The main administrative responsibilities include:
•	Reviewing student resource requests.
•	Approving resource requests.
•	Rejecting resource requests.
•	Managing campus announcements.
•	Viewing administrative information.
6. Learning Resource Management
6.1 Resource Page
The Learning Resources page provides students with access to educational materials.
Its metadata identifies the page as:
Title: Learning Resources
Description: Explore study guides, programming notes, and career resources on CampusConnect.
The page renders the ResourcesClient component, which manages the interactive resource interface.
Students can:
•	Browse available resources.
•	View resource titles and descriptions.
•	Explore resource categories.
•	Request access to learning materials.
•	Check their request statuses.
•	Download approved resources.
6.2 Resource Access Request Process
The resource request system connects the student interface with the administrator's review interface.
The process begins when a student selects a learning resource and submits an access request.
The application checks whether the student has a saved session and whether an equivalent pending or approved request already exists.
If the request is valid, it is saved in Local Storage.

Each request contains information such as:
•	Request ID.
•	Resource ID.
•	Resource title.
•	Student email.
•	Request status.
•	Creation date.
A newly submitted request receives the pending status.
6.3 Request Status Management
The application uses three main request statuses.
Status	Description
Pending	The request has been submitted and is waiting for administrator review.
Approved	The administrator has approved the request.
Rejected	The administrator has rejected the request.
These statuses allow students to understand the progress of their requests.
A rejected request can be submitted again through the existing request workflow.
6.4 Administrator Request Review
The administrator reviews submitted requests through the AdminResourceRequestsClient component.
The administrator can:
1.	View submitted student requests.
2.	Review the requested resource.
3.	Check the student's request information.
4.	Approve a request.
5.	Reject a request.
When an administrator changes a request status, the updated information is saved in Local Storage.
The student interface can then display the updated status.
6.5 Resource Access and Downloads
The application controls the resource download interface according to the request status.
•	Pending requests display a waiting status.
•	Approved requests allow the corresponding download.
•	Rejected requests display their rejection status and allow a new request through the existing workflow.
The application uses resource download URLs or corresponding PDF paths to provide access to approved materials.
The actual download files must exist in the public resources location for their links to work.
7. Student Report Generation
CampusConnect includes a student report request and download feature.
The report follows an approval-based workflow.
1.	A student submits a report access request.
2.	The request is saved with a pending status.
3.	The administrator reviews the request.
4.	The administrator approves or rejects it.
5.	After approval, the student can generate and download the PDF report.
The report uses CSV data as its source.
The application uses:
•	CSV: Provides structured student information.
•	jsPDF: Generates the PDF document.
•	jspdf-autotable: Formats tabular information in the PDF.
The report functionality demonstrates data processing and document generation.
The CSV should contain fictional demonstration data rather than confidential student information.
8. Announcement Management
8.1 Announcement System
The announcement feature provides a centralized place for important campus updates.
Students can access announcements through the announcements page.
Announcements are organized into four categories:
•	Academic.
•	Campus.
•	Opportunity.
•	Notice.
This organization makes it easier for students to identify relevant information.
8.2 Administrator Announcement Management
Administrators can create and manage announcements through the administrative interface.
The announcement management functionality allows administrators to maintain campus information that students can view.
The application uses the browser Local Storage key campusConnectAnnouncements to maintain announcement information.
This makes announcement updates available within the same browser environment, but does not automatically distribute them to other users or devices.
9. Metadata and SEO
CampusConnect uses the Next.js Metadata API to configure page-specific information.
Metadata provides information about the page to browsers and search engines.
9.1 Page Titles
The title property defines the title displayed in the browser tab and commonly used in search results.
Example:
export const metadata = {
  title: "Learning Resources",
};
9.2 Page Descriptions
The description property summarizes the content of a page.
Example:
export const metadata = {
  title: "Learning Resources",
  description:
    "Explore study guides, programming notes, and career resources on CampusConnect.",
};


9.3 Metadata for Different Pages
CampusConnect uses page-specific metadata for different areas.
Page	Metadata Purpose
Learning Resources	Describes educational materials available to students.
Admin Dashboard	Describes administrative request management.
Student Dashboard	Identifies the student dashboard.
Events	Describes available campus activities.
Event Details	Describes individual campus events.
Announcements	Identifies campus announcements.
9.4 Open Graph and Robots Metadata
Open Graph metadata provides information for supported social sharing previews, such as page titles, descriptions, and images.
Robots metadata controls search engine indexing preferences.
These metadata configurations improve how supported pages are presented and discovered.
9.5 Server and Client Components
The application separates page metadata from interactive functionality.
Server Component page files export metadata and render Client Components.
For example, the Learning Resources page exports metadata and renders ResourcesClient.
This allows metadata to remain configured on the server while React handles interactive browser functionality.
10. React State Management
CampusConnect uses React hooks to manage interactive components and changing application information.
10.1 useState
useState manages component state.
Examples include:
•	Current student information.
•	Search queries.
•	Selected event categories.
•	Form inputs.
•	Resource request information.
•	Announcement information.
•	Loading and error states.
When the state changes, React updates the relevant interface.
Example:
const [user, setUser] = useState(null);
This creates a state variable for user information and a function to update it.
10.2 useEffect
useEffect handles side effects after a component renders.
CampusConnect uses it for tasks such as:
•	Reading saved session information.
•	Loading information from Local Storage.
•	Checking whether a student is signed in.
•	Loading resource requests.
•	Listening for browser storage events.
•	Synchronizing displayed request information.
Example:
useEffect(() => {
  const savedSession = localStorage.getItem(
    "campusConnectSession"
  );
  if (!savedSession) {
    router.replace("/signin?error=auth");
    return;
  }
  setUser(JSON.parse(savedSession));
}, [router]);

In this example, the component checks for a saved student session after rendering.
If the session is missing, the user is redirected to the sign-in page.
If the session exists, the user information is loaded into React state.
10.3 State and Storage Updates
React state controls what is displayed in the interface, while Local Storage preserves selected information in the browser.
The application uses browser storage events and custom events in relevant components to update displayed information after data changes.
This supports the prototype's interactive behavior without requiring a connected database.
11. API Functionality
CampusConnect includes Next.js Route Handlers for application API functionality.
11.1 Events API
The events API provides event-related data.
It supports filtering using query parameters such as search terms and categories.
The endpoint demonstrates retrieving and filtering event information through a Next.js API route.
The current API uses the project's sample event data; browser-created Local Storage events are not automatically included in server API responses.
11.2 Health-check API
The health-check API provides a simple endpoint for checking whether the application is responding.
It can be used to verify basic application availability.
The health-check endpoint is separate from user authentication and resource request management.
12. HTTP Status Codes and Request Responses
HTTP status codes communicate the result of a request between a client and a server.
The following codes describe the expected responses relevant to CampusConnect API operations.
Status Code	Response Message	Meaning
201	Resource created successfully	A new resource or request was successfully created.
400	Invalid request data	The submitted information is missing or invalid.
401	Authentication required or failed	Authentication is missing or unsuccessful.
403	Access forbidden	The authenticated user does not have permission.
404	Resource not found	The requested resource or record does not exist.
500	Internal server error	An unexpected server-side error occurred.
12.1 201 — Created
Indicates that a new resource or request has been successfully created by an API.
In CampusConnect, this is the appropriate response for a successful server-side resource request creation.
The current Local Storage implementation saves requests in the browser and does not itself return HTTP 201.
12.2 400 — Bad Request
Indicates that the submitted request contains invalid or missing information.
Examples include missing resource identifiers or invalid request fields.
CampusConnect also performs client-side form validation to prevent incomplete submissions.
12.3 401 — Unauthorized
Indicates that authentication is required or has failed.
The student interface checks for a saved session and redirects unauthenticated users to sign-in.
This browser redirect is not itself an HTTP 401 response.
12.4 403 — Forbidden
Indicates that an authenticated user does not have permission to perform an action.
For example, a student should not be permitted to perform administrator-only operations.
The current Local Storage-based admin check provides frontend separation but does not enforce secure server-side authorization.
12.5 404 — Not Found
Indicates that the requested resource, record, or route cannot be found.
Examples include:
•	An event ID that does not exist.
•	A missing resource record.
•	An unavailable download file.
•	An unknown application route.
Next.js supports not-found handling through its routing conventions.
12.6 500 — Internal Server Error
Indicates that an unexpected error occurred while processing a server-side request.
Next.js provides error boundaries for rendering errors.
CampusConnect uses app/error.js to display a friendly error interface and provide a retry action.
The error boundary does not automatically generate an HTTP 500 response for every error. API Route Handlers must return their own appropriate error responses.
13. Error Handling
CampusConnect uses Next.js error-handling functionality to provide a better user experience.
13.1 Error Boundary
The app/error.js component handles unexpected errors in its covered route segments.
It displays:
•	A friendly error message.
•	An explanation that the page could not be loaded.
•	A retry button.
13.2 Retry Functionality
The retry button calls Next.js reset().
This attempts to render the affected route segment again.
13.3 Form Validation
The application validates user input before accepting certain actions.
Examples include:
•	Required student registration fields.
•	Student credentials.
•	Event title and description.
•	Event date, time, and location.
•	Resource access requests.
Validation messages help users understand unsuccessful submissions.
14. Data Storage
CampusConnect currently uses browser Local Storage for its frontend prototype.
The main storage areas include:
Storage Key	Purpose
campusConnectUser	Stores the demo student account.
campusConnectSession	Stores the student session.
campusConnectAdminSession	Stores the administrator session.
campusConnectEvents	Stores newly created events.
campusConnectAnnouncements	Stores announcement information.
campusConnectResourceRequests	Stores submitted resource requests and their statuses.
Sample events, resources, and announcements are also provided by the application.
14.1 Storage Limitations
Local Storage is specific to the browser and device.
Therefore:
•	Information is not automatically shared across different users.
•	Data does not automatically synchronize between devices.
•	Clearing browser storage can remove saved information.
•	Browser-stored sessions and request statuses can be modified by users.
The current implementation is suitable for demonstrating frontend functionality, not for handling confidential production data.

16. Current Project Limitations
•	No backend database is connected.
•	Account and session information is stored in browser Local Storage.
•	Newly created events are not automatically shared across devices.
•	Announcement updates are not centrally synchronized between different users.
•	Resource requests are not managed through a shared backend.
•	Local Storage does not provide secure authentication or authorization.
•	Some displayed content uses sample data.
•	API event data does not automatically include browser-created events.
17. Future Improvements
Potential improvements include:
•	Integrating a database for persistent and shared information.
•	Implementing secure authentication and server-side authorization.
•	Introducing centralized resource request management.
•	Supporting shared announcement updates.
•	Adding event registration and attendance tracking.
•	Allowing students to edit and delete their own events.
•	Improving accessibility and automated testing.
•	Adding more comprehensive API validation and error responses.
18. Conclusion
CampusConnect demonstrates the development of a student community platform using Next.js and React.
It brings together student activities, event management, announcements, learning resources, resource request workflows, and administrative functionality.
The project demonstrates practical application of component-based development, React state management, client-side authentication flows, Local Storage, Next.js metadata, API Route Handlers, form validation, and error handling.
Through its student and administrator experiences, CampusConnect provides an organized example of how a digital platform can support campus communication and student engagement.
